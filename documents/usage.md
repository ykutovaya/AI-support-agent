## Обмен и возврат

Вверху экрана указаны выбранное обращение и следующий шаг. Сохранённые обращения находятся слева, создание нового — в раскрываемом блоке. Выбор сохраняется в адресе страницы: обновление восстанавливает это же обращение. Технический журнал доступен в «Подробностях».

После исполнения отдельно показаны результат в магазине, заявка специалисту, ответ и доставка, сохранённая проверка. Время проверки не меняется при просмотре; старым записям неизвестная дата не добавляется. Просмотр результата Zammad не обращается к облаку.

Для стандартного запуска из README используется собственный синтетический магазин `evals/reapproval/base_shop.json`:

1. Выбрать клиента `user1@example.test`, нажать «Новое обращение».
2. Ввести «Обменяйте товар на любой другой доступный вариант. Email user1@example.test» и нажать «Подготовить решение». В исходном учебном магазине это заказ `#O1`, замена `old` на `new`, доплата 2,35 USD. Для возврата в новом снимке можно использовать «Хочу вернуть товар. Email user1@example.test».
3. Проверить историю, источники, товар, сумму, способ оплаты и точный текст. Заглушка ищет доставленный заказ среди первых шести заказов клиента, выбирает одну позицию и первый другой доступный вариант; произвольные предпочтения по цвету и другим свойствам она не разбирает.
4. Подтвердить отправку запроса условий клиенту. В блоке «Ответ клиента — тестовый канал» ввести ответ и нажать «Клиент согласен» либо «Клиент отказался».
5. При согласии клиента проверить новое предложение «Действие и ответ» и отдельно подтвердить его. При отклонении сотрудником указать причину: новый проект снова потребует согласования.

Ответ клиента здесь имитирует оператор. Кнопки фиксируют явный выбор; приложение не проверяет согласие автоматически по свободному тексту. Локальный сотрудник имеет фиксированный идентификатор `demo-employee`, реального входа и управления ролями нет.

Обмен создаёт статус `exchange requested`, возврат — `return requested`. Деньги не списываются и не возвращаются; письмо не отправляется. Тестовая доставка сохраняет утверждённый текст в SQLite. Повтор после сбоя доставки отправляет прежний текст без повторения операции.

Три отдельных обращения — обычный обмен, изменение цены и передача специалисту — подготовлены в [инструкции приёмки](evaluation/acceptance.md). Они используют другую учебную базу.

## Повторный запуск и доставка

Для повторного запуска повторите блок запуска с прежним `SUPPORT_AGENT_DB`, затем выберите сохранённое обращение. Если операция уже записана, но ответ остался в очереди, нажмите «Продолжить отправку»; при ошибке доставки — «Повторить отправку». Обе команды используют прежнее согласование, текст и идентификатор сообщения. Само открытие экрана ничего не отправляет. Если терминал был закрыт, задайте переменные из блока запуска заново.

Остановка выполняется через `Ctrl+C` в терминале. Проверенная конфигурация — `127.0.0.1` и Streamlit 1.56.0. [Ограничения остановки Windows](architecture.md#остановка-локального-сервера), [проверка установки и восстановления](evaluation/startup.md).

## Изменение условий

Если условия изменились, старое предложение блокируется, а согласие клиента отзывается. В режиме `manual` сотрудник видит причину и нажимает «Продолжить расследование». В режиме `auto` карточка показывает значения «было / стало», и приложение готовит новую версию автоматически. Для неё снова нужны подтверждение отправки условий, ответ клиента и подтверждение действия сотрудником. Повторная смена цены запускает тот же процесс; отказ клиента останавливает его, даже если цена уже изменилась.

Режим пересогласования задаётся независимо от модели, например `$env:SUPPORT_AGENT_RECOVERY_MODE = 'auto'` перед запуском. Переключателя внутри обращения нет. При остановке процесса во время подготовки новая версия автоматически не возобновляется: новое сообщение клиента отменяет незавершённое продолжение и начинает расследование заново.

## Локальная заявка специалисту

После регистрации обмена или возврата в том же обращении введите: **«Проверьте результат обмена. Email user1@example.test»**. Агент проверит клиента и заказ и подготовит карточку локальной заявки. Проверьте её содержание и точный ответ, затем нажмите **«Подтвердить действие и ответ»**. В результате появятся номер `T-1` (или следующий свободный) и состояние `open`. Дополнительное согласие клиента для этой внутренней регистрации не требуется; требования согласия для обмена и возврата сохранены.

Для отдельного прохода с уже зарегистрированным обменом остановите сервер и запустите его с такими настройками:

```powershell
$env:SUPPORT_AGENT_MODE = 'demo'
$env:SUPPORT_AGENT_RECOVERY_MODE = 'manual'
$env:SUPPORT_AGENT_TICKET_BACKEND = 'local'
$env:SUPPORT_AGENT_RETAIL_DB = 'evals/ticket-integration/base_shop.json'
$env:SUPPORT_AGENT_DB = 'var/ticket-demo.sqlite3'
.\var\runtime\Scripts\python.exe -m streamlit run src/support_agent/ui.py --server.address 127.0.0.1 --server.port 8501 --server.headless true --browser.gatherUsageStats false
```

При первом запуске выберите `user1@example.test`, создайте обращение и введите вопрос выше. Для повторного запуска используйте ту же SQLite; чтобы начать новый учебный снимок, укажите новое имя базы. Существующие базы приёмки не перезаписывайте.

Заявка хранится в `support_tickets` той же SQLite, имеет номер, проверенное содержимое и состояние. Это локальная имитация: внешний сервис и специалист не подключены, обмен или выплата не считаются исполненными. Ответ сохраняется в тестовом канале. Повтор подтверждения или перефразирование того же вопроса в одном обращении не создают вторую заявку и доставку. Обновление экрана и перезапуск ничего не исполняют сами.

Данные отдельного прохода — собственный синтетический снимок в формате retail, а не новая задача исходного τ-bench. Учебная модель поддерживает вопрос о результате зарегистрированного обмена/возврата; произвольное понимание текста этими проверками не подтверждено. [Проверки и ограничения](evaluation/ticket-integration.md).

## Заявка в Zammad

| Свойство | `local` | `zammad` |
|---|---|---|
| Заявка | В SQLite | В настоящем Zammad |
| Атомарность | Заявка, результат и очередь ответа — одна транзакция | Запрос сохраняется до POST; транзакция SQLite не откатывает внешнюю запись |
| Неизвестный исход | Ошибка транзакции откатывает запись | Повтор создания и успешный ответ блокируются до явной проверки GET |
| Доставка после проверки | Прежний согласованный текст | Прежний согласованный текст; нового POST при повторе доставки нет |

В `.env` корня приложения задайте `ZAMMAD_URL` и `ZAMMAD_TOKEN` по [.env.example](../.env.example). Остальные настройки тоже можно хранить в `.env`; значения окружения имеют приоритет. Файл читается для настроек Zammad только при явном `SUPPORT_AGENT_TICKET_BACKEND=zammad` в окружении процесса. Это не включает API модели и не загружает её ключи в режиме `demo`.

В проверенном учебном экземпляре использованы группа `2` с именем `Retail Demo` и клиент `4`, явно сопоставленный синтетическому клиенту `u1`. Для другого экземпляра задайте его реальные ID. Команды из корня приложения:

```powershell
$env:SUPPORT_AGENT_MODE = 'demo'
$env:SUPPORT_AGENT_RECOVERY_MODE = 'manual'
$env:SUPPORT_AGENT_TICKET_BACKEND = 'zammad'
$env:ZAMMAD_GROUP_ID = '2'
$env:ZAMMAD_GROUP_NAME = 'Retail Demo'
$env:ZAMMAD_CUSTOMER_MAP = '{"u1":4}'
$env:SUPPORT_AGENT_RETAIL_DB = 'evals/zammad/base_shop.json'
$env:SUPPORT_AGENT_DB = 'var/zammad-demo.sqlite3'
if (Test-Path -LiteralPath $env:SUPPORT_AGENT_DB) { throw 'Для первого прохода выберите ещё несуществующий файл базы.' }
.\var\runtime\Scripts\python.exe -m streamlit run src/support_agent/ui.py --server.address 127.0.0.1 --server.port 8501 --server.headless true --browser.gatherUsageStats false
```

Снимок и соседний `policy.md` — собственные синтетические данные для Zammad. Прежние базы и правила локального сценария сохраняются. Откройте [рабочее место](http://127.0.0.1:8501), выберите `user1@example.test`, создайте обращение и введите **«Проверьте результат обмена. Email user1@example.test»**. Проверьте экземпляр Zammad, группу, клиента, содержание заявки и точный ответ; нажмите **«Подтвердить действие и ответ»**. До подтверждения внешняя заявка не создаётся. После создания приложение читает заявку и сверяет её поля; только проверенный результат разрешает доставку согласованного ответа. Карточка показывает номер, состояние и ссылку.

При неизвестном исходе нажмите **«Проверить результат в Zammad»**: выполняется только чтение, повторного создания нет. Если результат не найден или поля не совпали, сообщение об успехе остаётся заблокированным. Перезапуск, повторное подтверждение, перефразирование вопроса и переключение на локальный режим не обходят сохранённую операцию. Автоматических повторов нет. Для продолжения после перезапуска используйте прежнюю SQLite и повторите команду запуска сервера; при сбое доставки кнопка её повтора использует прежний текст и идентификатор. Добавление номера в текст требует нового подтверждения сотрудником.

Отсутствие заявки в первой выдаче не доказывает отсутствие записи. Срок поиска не гарантируется. При недоступности пробного экземпляра сохраняются локальный запуск, проверки с заглушкой API и записанные результаты. Создание заявки не подтверждает решение вопроса специалистом, исполнение обмена или выплату.

Для повторного запуска с прежней базой заново задайте настройки и выполните строку запуска Streamlit. Проверка `Test-Path` в примере относится только к первому проходу. Подробности создания и восстановления на настоящем API — в [отчёте Zammad](evaluation/zammad-integration.md).

## Настройки

| Настройка | Поведение |
|---|---|
| `SUPPORT_AGENT_MODE` | `demo` по умолчанию; `api` нужно включить явно в окружении процесса |
| `SUPPORT_AGENT_TICKET_BACKEND` | `local` по умолчанию; `zammad` нужно включить явно в окружении процесса. Режим модели не меняется |
| `SUPPORT_AGENT_RECOVERY_MODE` | `manual` по умолчанию; `auto` включает показ разницы и автоматическую подготовку новой версии. Согласования остаются ручными |
| `SUPPORT_AGENT_DB` | Рабочая SQLite; в основном запуске `var/demo.sqlite3`. Если переменная не задана, код использует `var/support.sqlite3` относительно корня приложения |
| `SUPPORT_AGENT_RETAIL_DB` | JSON исходного магазина; в основном запуске `evals/reapproval/base_shop.json`. `policy.md` читается рядом. Если переменная не задана, код ожидает `../tau2-bench/data/tau2/domains/retail/db.json` |
| `OPENAI_API_KEY`, `OPENAI_MODEL` | В режиме `api` берутся из окружения либо `.env` корня приложения; окружение имеет приоритет. Модель по умолчанию — `gpt-6-luna` |
| `ZAMMAD_URL`, `ZAMMAD_TOKEN` | Адрес экземпляра HTTPS и токен API; читаются из окружения либо `.env` только при получателе `zammad` |
| `ZAMMAD_GROUP_ID`, `ZAMMAD_GROUP_NAME` | Положительный ID и точное имя группы Zammad; входят в согласуемые условия |
| `ZAMMAD_CUSTOMER_MAP` | JSON-объект соответствия клиента retail существующему ID клиента Zammad, например `{"u1":4}`. Неуказанный клиент блокирует подготовку внешней заявки |

## Новый рабочий снимок

Исходный магазин и правила копируются в рабочую SQLite только при её первой инициализации. Следующие запуски читают сохранённый снимок и историю; изменение исходного `db.json` или `policy.md` не обновляет существующую рабочую базу. Оригинальные данные τ-bench не изменяются.

Для нового прохода без API остановите сервер. Задайте настройки `demo/manual/local` и путь к исходному магазину из блока запуска в README, затем выберите ещё несуществующий файл базы:

```powershell
$env:SUPPORT_AGENT_DB = 'var/support-new.sqlite3'
if (Test-Path -LiteralPath $env:SUPPORT_AGENT_DB) { throw 'Выберите ещё несуществующий файл базы.' }
.\var\runtime\Scripts\python.exe -m streamlit run src/support_agent/ui.py --server.address 127.0.0.1 --server.port 8501 --server.headless true --browser.gatherUsageStats false
```

Сохраняйте прежний файл базы; удаление истории для нового прохода не требуется. Остальные настройки остаются как в блоке первичного запуска. Изменение режима, путей, ключа или модели также требует перезапуска сервера.

## Проверка без API

Для проверки двух известных ответов без ключей и обращения к модели используйте отдельную команду. Она проходит поиск по имени и индексу с последующим обменом и отказ от обмена после прежнего согласия:

```powershell
.\var\runtime\Scripts\python.exe -m evals.investigation.check_known_replies --set name-zip-refusal --output evals/investigation/offline-final-new
```

Каталог результата должен быть новым. Модель, клиент и сотрудник подставные; в отчёте сохраняются действия, согласования и точные доставленные тексты. [Результаты](evaluation/investigation.md#итоговая-техническая-проверка-без-api).

## Настоящая модель

Для работы с моделью задать ключ в окружении либо `.env` корня приложения по [.env.example](../.env.example), установить `$env:SUPPORT_AGENT_MODE = 'api'` и перезапустить сервер. Подготовка решения и его пересмотр могут обращаться к API. Создание сервиса само модель не вызывает. При `demo/local` файл `.env` не читается; при `demo/zammad` из него используются только настройки Zammad, API модели остаётся выключенным. Лимит 5 USD из эксперимента пересогласования не ограничивает расходы рабочего места в режиме API.
