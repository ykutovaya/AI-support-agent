# τ-bench retail: данные, ситуации клиентов и инструменты

Разбор локальной версии τ-bench. Данные синтетические. Количества ниже подсчитаны по исходным JSON, до выполнения операций агента.

Источники в репозитории `tau2-bench`:

- `data/tau2/domains/retail/db.json` — данные магазина;
- `data/tau2/domains/retail/tasks.json` — сценарии и критерии проверки;
- `src/tau2/domains/retail/tools.py` — реализация операций;
- `src/tau2/domains/retail/data_model.py` — типы и поля данных;
- `src/tau2/evaluator/` — вычисление результатов проверки.

`tools.py` находится в `src`, а не в каталоге данных `data`.

## 1. Как представлены клиенты, товары и заказы

`db.json` — JSON-объект с тремя словарями. Ключ каждой записи совпадает с её идентификатором.

| Словарь | Содержимое | Количество |
|---|---|---:|
| `users` | Клиенты по `user_id` | 500 |
| `products` | Товары по `product_id` | 50 |
| `orders` | Заказы по `order_id` | 1000 |

У 50 товаров суммарно 591 вариант. Отдельного верхнеуровневого словаря вариантов нет: они вложены в товары.

### Клиенты: `users`

| Поле | Содержимое |
|---|---|
| `user_id` | Идентификатор клиента, например `yusuf_rossi_9620` |
| `name` | Объект с `first_name` и `last_name` |
| `email` | Адрес электронной почты |
| `address` | Адрес по умолчанию |
| `payment_methods` | Словарь способов оплаты по их идентификаторам |
| `orders` | Список идентификаторов заказов; сами заказы хранятся в `orders` |

Адрес содержит `address1`, `address2`, `city`, `state`, `country`, `zip`.

У способа оплаты есть `id` и `source`. Остальные поля зависят от типа:

| `source` | Дополнительные поля | Количество записей |
|---|---|---:|
| `credit_card` | `brand` — платёжная система, `last_four` — последние четыре цифры | 239 |
| `gift_card` | `balance` — баланс подарочной карты | 234 |
| `paypal` | Дополнительных полей нет | 222 |

Это число способов оплаты, а не клиентов: у клиента может быть несколько способов.

### Товары: `products`

Товар содержит `product_id`, `name` и словарь `variants`. Товар описывает модель, а вариант — конкретное сочетание характеристик.

Например, `1656367028` — `Mechanical Keyboard`. Один из его вариантов, `7706410293`:

```json
{
  "item_id": "7706410293",
  "options": {
    "switch type": "clicky",
    "backlight": "none",
    "size": "full size"
  },
  "available": true,
  "price": 269.16
}
```

У варианта есть:

- `item_id` — идентификатор варианта, отличный от `product_id`;
- `options` — характеристики; их набор зависит от товара;
- `available` — признак наличия;
- `price` — текущая цена в каталоге.

В данном файле все `item_id` уникальны между товарами. Количества единиц на складе нет: наличие представлено только значением `true` или `false`.

### Заказы: `orders`

| Поле | Содержимое |
|---|---|
| `order_id` | Идентификатор с символом `#`, например `#W2378156` |
| `user_id` | Ссылка на владельца заказа в `users` |
| `address` | Адрес доставки именно этого заказа |
| `items` | Список купленных позиций |
| `status` | Статус заказа |
| `fulfillments` | Список отправок |
| `payment_history` | История оплат и возвратов денег |

Каждая позиция `items` содержит `name`, `product_id`, `item_id`, `price`, `options`. Здесь `price` — цена при покупке, а не автоматически обновляемая цена каталога. Отдельного `quantity` нет: количество одинаковых вариантов определяется числом повторений `item_id` в списке.

Адрес профиля и адрес заказа хранятся отдельно. Изменение адреса профиля само по себе не меняет адреса существующих заказов.

В каждой отправке `fulfillments` находятся два списка: `tracking_id` — номера отслеживания, `item_ids` — отправленные варианты товаров.

Запись `payment_history` содержит:

- `transaction_type`: `payment` или `refund`;
- `amount`: сумму;
- `payment_method_id`: ссылку на способ оплаты владельца заказа.

В исходном файле 1000 записей `payment` и 102 записи `refund`. Например, у отменённого заказа `#W3220387` есть оплата и возврат по `608.91` через один способ PayPal.

Статусы исходных заказов:

| Статус | Значение | Количество |
|---|---|---:|
| `pending` | Ожидает обработки | 423 |
| `delivered` | Доставлен | 373 |
| `processed` | Обработан | 102 |
| `cancelled` | Отменён | 102 |

Поля результата обмена и возврата, такие как `exchange_*` и `return_*`, отсутствуют в исходном JSON. Они предусмотрены моделью данных и заполняются инструментами в ходе симуляции.

В заказах нет отдельной даты создания. В суммах и ценах нет отдельного поля валюты.

### Как связаны записи

Конкретный пример из файла:

1. В `users["yusuf_rossi_9620"].orders` есть `#W2378156`.
2. У `orders["#W2378156"]` указан тот же `user_id`, статус `delivered` и пять позиций.
3. Одна из позиций — клавиатура с `product_id = "1656367028"`, `item_id = "1151293680"` и ценой покупки `272.33`.
4. Её описание в каталоге находится в `products["1656367028"].variants["1151293680"]`.
5. Оплата всего заказа — `1819.92` через `credit_card_9513926`. Этот способ оплаты находится в профиле владельца заказа.

В нашем прототипе `users` может представлять сведения CRM, а `products` и `orders` — данные магазина. Правила находятся в отдельном `policy.md`; обращений и переписки с клиентами в `db.json` нет.

## 2. Ситуации клиентов и критерии проверки

В `tasks.json` находятся 114 сценариев с идентификаторами от `"0"` до `"113"`. Это описания поведения имитатора клиента, а не готовые диалоги.

### Какие ситуации встречаются

Группы пересекаются: одно обращение часто содержит несколько просьб.

| Ситуация | Примеры задач | Что требуется от агента |
|---|---|---|
| Найти клиента и заказ по неполным сведениям | `45–47` | Уточнить ошибочный номер заказа; учитывать, что клиент может забыть часть номера или email |
| Ответить о товарах и доставке | `2`, `43` | Посчитать доступные варианты, найти характеристики, адрес и номер отслеживания |
| Изменить необработанный заказ | `3–4`, `60–61` | Подобрать нужные характеристики, учесть ограничения цены и наличие |
| Обменять доставленные товары | `0–1`, `95` | Учесть предпочтения, собрать все позиции и рассчитать разницу цен |
| Вернуть товары из одного или нескольких заказов | `19`, `28`, `104` | Выбрать нужные позиции, сохранить остальные и учесть ограничения операций |
| Отменить заказ или отказаться от отмены | `24`, `113` | Уточнить причину и актуальное намерение клиента, отменить только допустимые заказы |
| Изменить адреса | `22`, `87` | Различать адрес профиля и адреса заказов; учитывать последующие изменения намерения |
| Разобраться с оплатой | `40`, `95` | Проверить способ оплаты, баланс подарочной карты, доплату или возврат разницы |
| Отказать или передать человеку | `10`, `50`, `65` | Не выполнять недоступную операцию, например восстановление отменённого заказа или обмен на другой тип товара |

В задачах `0` и `1` клиент хочет обменять клавиатуру и термостат. Различие — в допустимом компромиссе. Если нет нужной клавиатуры, в `0` клиент согласен на вариант без подсветки, а в `1` хочет обменять только термостат.

В задаче `5` намерение меняется при согласовании: сначала клиент просит обменять два товара, затем только лампу, затем отказывается от обмена и просит вернуть бутылку. Такие изменения уже входят в набор.

### Что хранится в задаче

| Поле | Назначение |
|---|---|
| `id` | Идентификатор задачи |
| `user_scenario.instructions.task_instructions` | Как имитатор должен вести себя в разговоре |
| `reason_for_call` | Причина обращения, пожелания и условия выбора |
| `known_info`, `unknown_info` | Какие сведения клиент знает или не помнит |
| `description` | Служебное описание цели и замечаний; многие значения пусты |
| `initial_state` | Дополнительные настройки начального состояния; во всех 114 задачах здесь `null` |
| `evaluation_criteria` | Эталонные действия и условия проверки |
| `issues` | Замечания к отдельным сценариям; есть у задач `4`, `5`, `7` |

`reason_for_call`, `known_info` и `unknown_info` вложены в `user_scenario.instructions`.

### Как проверяется результат

В `evaluation_criteria` находятся четыре поля:

- `actions` — один эталонный способ решить задачу;
- `communicate_info` — сведения, которые нужно сообщить;
- `nl_assertions` — требования к разговору, записанные обычным текстом;
- `reward_basis` — какие проверки входят в итоговую оценку.

**Проверка `DB`.** Проверяющая программа создаёт исходную среду и выполняет в ней эталонные `actions`. Отдельно восстанавливает результат действий агента. Затем сравнивает хеши данных. Совпадение даёт `1`, различие — `0`.

Совпадать должна конечная база, а не последовательность вызовов. Агент может найти сведения другим способом и пройти проверку. В этой выборке `ACTION` не включён в `reward_basis` ни одной задачи.

**Проверка `NL_ASSERTION`.** Отдельная языковая модель проверяет требования к разговору. Если выполнены все требования, результат равен `1`, иначе `0`. Пустой список или `null` даёт `1` без содержательной проверки текста.

Для данного файла:

- у 112 задач `reward_basis = ["DB", "NL_ASSERTION"]`;
- у задач `33` и `34` — только `["DB"]`;
- непустые `nl_assertions` есть у 40 задач;
- непустые `communicate_info` есть у 36 задач, но `COMMUNICATE` не входит в `reward_basis` ни одной из 114 задач. При обычном режиме оценки это поле само по себе не добавляет отдельную проверку результата.

Для большинства задач формула такова:

```text
reward = DB × NL_ASSERTION
```

Например, в задаче `2` нужно оформить возврат трёх товаров и сообщить, что доступно 10 вариантов футболок. Эталонные действия задают нужное изменение заказа, а `nl_assertions` — требование к ответу о количестве вариантов.

В задаче `24` эталонный список `actions` пуст: клиент передумал отменять заказ. База должна остаться без изменений, а в ответе нужно назвать материалы футболок — полиэстер и хлопок.

Оценка не доказывает соблюдение всех правил. Например, правильная конечная база сама по себе не подтверждает, что агент спросил согласие клиента. В задачах с пустыми текстовыми проверками этот аспект может не влиять на итоговый балл. В файле также есть открытые замечания `issues`, поэтому спорные результаты нужно разбирать по диалогу и условиям конкретной задачи.

Имитатору клиента нужны инструкции сценария. Агенту поддержки нельзя передавать эталонные `evaluation_criteria` или скрытые подсказки из инструкций имитатора.

Эти количества и критерии относятся именно к локальному `tasks.json`. Другие наборы и языковые пакеты могут отличаться.

## 3. Что фактически делают инструменты

Функции работают с объектом `self.db`, содержащим данные магазина. Ниже описаны тела функций, а не обещания в комментариях. Вызов инструмента может изменить состояние симуляции; реальных банковских переводов, доставки и отправки писем в этом файле нет.

### Поиск и чтение

| Функция | Фактическое действие |
|---|---|
| `find_user_id_by_email(email)` | Перебирает клиентов и возвращает единственный подходящий `user_id` |
| `find_user_id_by_name_zip(first_name, last_name, zip)` | Ищет по имени, фамилии и почтовому индексу |
| `get_user_details(user_id)` | Возвращает профиль, способы оплаты и список заказов |
| `get_order_details(order_id)` | Возвращает заказ по точному идентификатору |
| `get_product_details(product_id)` | Возвращает товар и все его варианты |
| `get_item_details(item_id)` | Ищет вариант среди всех товаров и возвращает его |
| `list_all_product_types()` | Возвращает JSON-строку со словарём «название товара → product_id», отсортированным по названиям |

Email, имя и фамилия сравниваются без учёта регистра, диакритики и крайних пробелов. Внутренние пробелы и знаки препинания сохраняются. Почтовый индекс сравнивается точно.

Если совпадений нет, поиск клиента вызывает `ValueError("User not found")`; если их несколько — `ValueError("User lookup is ambiguous")`. Чтение по неизвестному идентификатору также вызывает ошибку.

Поиск по email не проверяет владение почтой. Функции чтения сами не проверяют, подтверждена ли личность клиента и принадлежит ли запрошенный заказ текущему собеседнику.

### Отмена: `cancel_pending_order(order_id, reason)`

Проверяет:

1. Заказ существует и имеет точный статус `pending`.
2. Причина — `no longer needed` или `ordered by mistake`.

Затем для каждой записи `payment_history` создаёт запись `refund` с той же суммой и способом оплаты. На каждом шаге находит способ оплаты владельца заказа; если он не найден, возникает ошибка. Для подарочной карты сразу увеличивает баланс в модели данных и округляет до двух знаков. Проверка способов оплаты и изменение балансов идут в одном цикле; общего отката при ошибке в самом методе нет.

У заказа устанавливает `status = "cancelled"`, сохраняет `cancel_reason` и добавляет записи возврата в `payment_history`. Возвращает обновлённый заказ.

Цикл проходит по всей истории платежей, не отбирая только записи `payment`. Ожидание 5–7 рабочих дней и банковский перевод здесь не реализованы.

### Возврат: `return_delivered_order_items(order_id, item_ids, payment_method_id)`

Проверяет:

1. Заказ существует и имеет статус `delivered`.
2. Способ получения средств есть в профиле владельца заказа.
3. Это подарочная карта либо способ оплаты из первой записи `payment_history`.
4. Каждый запрошенный вариант есть в заказе в достаточном количестве. Повторяющиеся `item_id` учитываются по числу вхождений.

Устанавливает:

```text
status = "return requested"
return_items = отсортированный список item_ids
return_payment_method_id = выбранный способ получения средств
```

Возвращает обновлённый заказ. Это регистрация запроса: функция не рассчитывает сумму возврата, не меняет баланс или историю платежей, не удаляет товары из заказа и не отправляет письмо.

### Обмен: `exchange_delivered_order_items(order_id, item_ids, new_item_ids, payment_method_id)`

Проверяет:

1. Заказ существует и имеет статус `delivered`.
2. Старые варианты присутствуют в нужном количестве.
3. Списки старых и новых вариантов одинаковой длины.
4. Каждой старой позиции соответствует доступный новый вариант того же товара.
5. Способ оплаты есть в профиле владельца заказа.
6. Для подарочной карты требует `balance >= diff_price`, где `diff_price` — рассчитанная разница цен.

По входным парам рассчитывает:

```text
разница = сумма(текущая цена нового варианта − цена старой позиции при покупке)
```

Результат округляет до двух знаков. Положительное значение означает доплату, отрицательное — возврат разницы.

Например, для клавиатуры из заказа `#W2378156` замена `1151293680` за `272.33` на `7706410293` за `269.16` даёт разницу `−3.17` для этой позиции.

Функция устанавливает `status = "exchange requested"` и сохраняет:

- `exchange_items` — отсортированный список старых вариантов;
- `exchange_new_items` — отдельно отсортированный список новых вариантов;
- `exchange_payment_method_id` — способ оплаты;
- `exchange_price_difference` — рассчитанную разницу.

Два списка сортируются независимо, хотя расчёт выполняется по исходным парам.

Товары в `order.items` не заменяются. Платёж или возврат не проводится, баланс подарочной карты и история платежей не меняются. Письмо не отправляется, новый заказ не создаётся.

### Какие ограничения остаются за агентом

- Функции не получают и не проверяют явное согласие клиента или сотрудника. Это требование к поведению агента, а не параметр операций.
- При обмене нет параметра с согласованной суммой: разница пересчитывается по цене каталога в момент вызова.
- Повторный возврат или обмен того же заказа отклоняется из-за смены статуса: он уже не `delivered`.
- Пустые списки товаров для возврата и обмена явно не запрещены. Обмен на тот же вариант тоже явно не запрещён.
- `transfer_to_human_agents(summary)` возвращает только строку `"Transfer successful"`. Реального подключения сотрудника эта функция не выполняет.

Поэтому правила из `policy.md`, встроенные проверки инструментов и критерии из `tasks.json` нужно рассматривать отдельно: они покрывают разные части поведения агента.
