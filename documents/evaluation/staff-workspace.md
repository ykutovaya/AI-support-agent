# Проверка рабочего места сотрудника

Реализован локальный экран Streamlit с общим ядром, рабочим снимком retail в SQLite, отдельными согласиями клиента и сотрудника и тестовым каналом сообщений. Обязательный процесс раздела 3 проверяется без API; штатная платная оценка τ-bench не повторялась.

## Проверенные условия

| Требование | Проверка |
|---|---|
| Два режима карточки | Проект сообщения и действие с ответом; до подтверждения нет доставки или записи |
| Точное согласование | Идентификатор, версия, текст, параметры и сумма входят в проверяемое содержимое предложения |
| Согласие клиента | Принимается только для уже доставленного актуального запроса условий; отказ не разрешает операцию |
| Изменение условий | Новые цена, статус или правила блокируют старое предложение; нужен новый запрос и согласование |
| Отмена намерения | Старый вопрос нельзя подтвердить даже при ошибке модели на новой реплике |
| Доступ к данным | Чужой профиль, заказ и товар отклоняются до вызова штатного инструмента; сотрудник ограничен назначенными обращениями |
| Атомарность | Ошибка не сохраняет частичные изменения; состояние ошибки фиксируется под той же блокировкой SQLite |
| Повтор операции | Двойное подтверждение, перезапуск и конкурентные запросы не создают повторную запись |
| Отдельная доставка | Сбой или повтор отправки не повторяет обмен; постоянный идентификатор доставки исключает дубли в тестовом получателе |
| Обрыв после записи, до доставки | После восстановления экран предлагает продолжить прежнюю отправку; операция, согласование и идентификатор сообщения сохраняются |
| Посторонние изменения | Изменение другого заказа того же или другого клиента не требует лишнего согласования и не теряется при исполнении |
| Подложные инструкции | Клиентский или товарный текст не разрешает чтение чужого заказа и прямую запись; проверки используют навязанные ответы модели, не оценивая её устойчивость к убеждению |
| Продолжение диалога | Ядро получает отправленные условия, фактический результат и новые реплики, включая реплики при сбое модели |
| Полный путь через экран | Обращение → чтения → запрос согласия → ответ клиента → подтверждение сотрудника → заявка → согласованный ответ; затем восстановление в новом экземпляре приложения |

Предложения модели не исполняют запись: в приложении доступны `propose_exchange` и `propose_return`. Исполнитель отдельно вызывает `RetailTools` после проверок. В штатном адаптере τ-bench исходные инструменты и правила сохранены.

## Как проверяли

Итоговый прогон: **138 проверок прошли**, ошибок и пропусков нет. Ruff и проверка форматирования проходят. Локальный Streamlit ответил `ok` на проверку доступности; временный сервер после проверки остановлен. Хеши девяти исходных файлов τ-bench совпали с сохранённым манифестом контрольного прогона.

Проверки поведения добавлялись перед реализацией. Отдельные проверки воспроизвели и затем закрыли ошибки отмены, конкурентного подтверждения, запоздалой ошибки доставки и потери фактических сообщений в контексте. Streamlit проверен через `AppTest`, включая полный процесс с настоящим `RetailTools` на синтетическом магазине и восстановление SQLite.

Основные файлы: `tests/test_proposals.py`, `test_storage.py`, `test_retail.py`, `test_execution.py`, `test_workflow.py`, `test_workflow_regressions.py`, `test_recommendations.py`, `test_bootstrap.py`, `test_demo_model.py`, `test_ui.py`, `test_app_flow.py`. Существующие проверки ядра и адаптера сохранены.

Итоговый состав, число проверок, версии и хеши исходных данных приведены в [сводке проверки](../../evals/staff-workspace/2026-10-30/summary.json). Это собственные проверки приложения, а не новый результат τ-bench и не сравнение качества моделей.

## Что означает результат

При обмене и возврате сохраняется заявка `exchange requested` или `return requested`. Платёжные записи не изменяются. Ответ об исполнении формируется по проверенному статусу и прямо сообщает, что учебная система не выполняла списание, возврат денег или отправку письма. Тестовая доставка сохраняет согласованный текст в локальной SQLite.

Рабочий снимок загружается из публичного `db.json` один раз; исходные файлы не перезаписываются. Обращения, предложения, согласования, операции, очередь ответов и полученные сообщения хранятся отдельно от `RetailDB`.

## Ограничения

- По умолчанию используется заглушка модели с заданными правилами: одна позиция первого найденного доставленного заказа, для обмена — первый доступный другой вариант. Свободные предпочтения она не понимает. Это демонстрация процесса, а не качество ИИ.
- Адаптер API включается только через `SUPPORT_AGENT_MODE=api`. Его подключение проверено подменами без оплачиваемого запроса; качество живой модели на экране в этом этапе не измерялось.
- Сотрудник `demo-employee` — локальная учебная роль. Вход пользователей и интеграция с корпоративными правами отсутствуют. Проверки принадлежности записей работают внутри приложения, но не заменяют авторизацию внешнего сервиса.
- Ответ клиента вводится через явно обозначенный тестовый канал кнопками согласия или отказа. Автоматической проверки смысла произвольного текста и реального канала клиента нет.
- В приложении поддержаны чтения, обмен и возврат доставленных товаров. Отмена и изменение ожидающего заказа, CRM заказчика и ИТ-поддержка не подключены.
- Блокировка устаревших условий есть; автоматический показ разницы и эксперимент по восстановлению согласования не реализованы. Разделы 4–7 остаются за пределами этапа.
