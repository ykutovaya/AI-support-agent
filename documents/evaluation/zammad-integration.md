# Подключение Zammad — 3 ноября 2026 года

Реализация и проверка настоящего API выполнены. Ассистент прошёл обычное создание заявки и восстановление после управляемой потери ответа через Streamlit AppTest. В обоих случаях Zammad содержит одну проверенную заявку, а тестовый канал — один экземпляр согласованного ответа. Это программная проверка экрана; проход браузером и человеческая приёмка не проводились.

## Условия

Использованы собственные синтетические [магазин](../../evals/zammad/base_shop.json) и [правила](../../evals/zammad/policy.md). Заказ `#O1` клиента `u1` имеет статус `exchange requested`; вопрос — о фактическом результате обмена. Модель — `DemoModel`, вызовов API модели нет. Сообщения остаются в локальном тестовом канале.

Пробный экземпляр — `https://ai-support-agent.zammad.com`, группа `2` / `Retail Demo`, клиент Zammad `4`, явно сопоставленный клиенту retail `u1`. Сотрудник подтверждает экземпляр, группу, клиента, содержание заявки и точный ответ. Подготовка предложения не вызывает Zammad. Согласия клиента на обмен и возврат сохраняют прежние требования.

Стенд [check_live.py](../../evals/zammad/check_live.py) сохраняет параметры, вызовы HTTP без токена, согласованный запрос и ответ, контрольные точки SQLite и хеши кода. [Сводка проверки](../../evals/zammad/2026-11-03/validation.json) связывает результаты с проверенной версией. Рабочие SQLite находятся в исключённом из Git каталоге `artifacts/`.

## Настоящий API

| Сценарий | Результат Zammad | Итог после восстановления и повторного подтверждения |
|---|---|---|
| [Обычное создание](../../evals/zammad/2026-11-03/normal/result.json) | ID `3`, № `22003`, состояние `new`, группа `2`, клиент `4` | 1 POST, 1 согласование, 1 операция, 1 запись очереди, 1 доставка; локальных заявок 0 |
| [Потерянный ответ](../../evals/zammad/2026-11-03/lost-response/result.json) | ID `4`, № `22004`, состояние `new`, группа `2`, клиент `4` | 1 POST, 1 согласование, 1 операция, 1 запись очереди, 1 доставка; локальных заявок 0 |

При обычном проходе настоящий POST вернул `201`. Последующие GET прочитали заявку, тег операции и статью; проверены согласованные поля и начальное состояние. Только затем приложение сохранило результат и доставило прежний текст. Перезапуск и повторное подтверждение не изменили счётчики.

Отдельное [повторное чтение](../../evals/zammad/2026-11-03/readback.json) подтвердило совпадение восьми полей у обеих заявок: заголовка, SHA-256 содержимого, ID и имени группы, ID клиента, состояния `new`, типа статьи `note` и признака `internal=true`. Таблицы согласованных и прочитанных значений сохранены в артефакте; тексты заявок здесь не дублируются.

В сценарии потери ответа настоящий POST также вернул `201` и создал заявку. Стенд намеренно скрыл этот ответ от адаптера, имитируя потерю подтверждения после записи. Приложение сохранило `unknown`; операций, очереди и доставок было **0**, согласование сохранилось. Первый поиск GET вернул HTTP `200`, но не подтвердил исход. Первоначальный [result-initial.json](../../evals/zammad/2026-11-03/lost-response/result-initial.json) сохранён со статусом `incomplete` и ошибкой проверки; он не заменён успешным результатом.

Примерно через шесть минут явный `--resume` в новом процессе нашёл заявку по постоянному тегу операции. После чтения и сверки заявки, тега и статьи исход стал подтверждённым; доставлен один экземпляр прежнего ответа. Второго POST не было. Такая задержка наблюдалась в этом прогоне; это не обещанный срок поиска. HTTP `200` от поиска сам по себе не подтверждает наличие подходящей заявки.

## Локальная и внешняя регистрация

| Свойство | `local` | `zammad` |
|---|---|---|
| Где находится заявка | `support_tickets` в SQLite | Во внешнем Zammad; SQLite хранит состояние операции |
| Атомарность | Заявка, результат и очередь ответа фиксируются одной транзакцией SQLite | До POST отдельно фиксируются идентификатор, запрос, согласование и текст; внешняя запись не откатывается транзакцией SQLite |
| Проверка результата | Чтение локальной записи | GET заявки, тега операции и статьи, сверка согласованных полей |
| Неизвестный исход | Сбой локальной транзакции откатывает запись | `submitting` / `unknown` блокируют повторное создание и успешный ответ; продолжение — только явное чтение результата |
| Доставка | Прежний текст с постоянным ключом доставки | То же; ошибка доставки не повторяет регистрацию |

Общий исполнитель сохраняет проверки сотрудника, версии, подписи и текущих условий. Перефразирование того же вопроса и смена получателя в одном обращении не создают повторную заявку. При неопределённом исходе нет автоматического повтора POST или перехода к локальной регистрации. Однозначный отказ API готовит новое сообщение для согласования; неподтверждённый успех клиенту не отправляется.

## Проверки без API

Проверены **389 тестов**. Общий [pytest.xml](../../evals/zammad/2026-11-03/offline/pytest.xml) содержит 378 успешных проверок и 11 ошибок подготовки из-за отсутствующего импорта тестовой фикстуры. Исправлен только её импорт; эти [11 проверок повторно прошли](../../evals/zammad/2026-11-03/offline/bootstrap-fixture-fixed.xml). Исходный отчёт сохранён, единого полностью успешного повторного прогона не заявляется.

Проверки охватывают доступ и согласование, изменение правил и получателя, подмену данных, отказы и неопределённый исход, конкурентное подтверждение, восстановление, повтор доставки, прежние retail-сценарии и экран. В числе 389 есть три проверки защиты непосредственно перед POST: сначала они выявили подмену сохранённых условий после подготовки операции, затем прошли после исправления. Отчёты [до исправления](../../evals/zammad/2026-11-03/offline/submit-integrity-red.xml) и [после него](../../evals/zammad/2026-11-03/offline/submit-integrity-green.xml) сохранены отдельно.

## Короткий демонстрационный проход

Настройки и команда запуска — в [README](../../README.md#заявка-в-пробном-zammad). Для нового прохода используется отдельная SQLite `var/zammad-demo.sqlite3`; существующие базы не перезаписываются.

1. Запустить `demo/manual` с получателем `zammad`, выбрать `user1@example.test` и создать обращение.
2. Ввести «Проверьте результат обмена. Email user1@example.test».
3. Проверить экземпляр, группу, клиента, заявку и точный ответ; подтвердить действие и ответ.
4. Проверить номер, состояние и ссылку. Обновление экрана и повторное подтверждение не создают ещё одну заявку.
5. Если исход неизвестен, нажать «Проверить результат в Zammad». При неподтверждённом результате оставить операцию заблокированной; повторное создание не запускать.

Без доступа к пробному экземпляру доступны [локальный запуск](../../README.md#локальная-заявка-специалисту), сохранённые результаты и обычный `python -m pytest` с заглушками API. Они воспроизводят проверки приложения, но не заменяют новую проверку облачного экземпляра. Стенд `check_live.py --run` обращается к настоящему API; `--resume` продолжает прежнюю попытку только чтением и требует сохранённой рабочей SQLite.

Дата окончания пробного доступа — **4 ноября 2026 года**, по подтверждению пользователя. Независимое подтверждение даты через API или браузер не получено. Для последующих демонстраций сохранены результаты, локальный режим и проверки с заглушкой API.

Человеческий проход Zammad пока не проведён; видео отложено. Это не отменяет выполненную программную проверку настоящего API. Проверены регистрация и восстановление в конкретном экземпляре, а не качество языковой модели, работа специалиста, внешняя доставка клиенту, фактический обмен или выплата. Исторические отчёты и базы прежней приёмки сохранены.
