# ИИ-агент поддержки

Локальное рабочее место сотрудника для обмена и возврата товаров на данных `retail` из τ-bench. Общее ядро расследует обращение; сотрудник проверяет предложение и точный ответ. После согласований исполнитель меняет рабочий снимок магазина в SQLite и передаёт сообщение в явно обозначенный тестовый канал. История сохраняется между запусками.

По умолчанию работает учебная заглушка без API и ручное продолжение после изменения условий. Автоматическое продолжение доступно как экспериментальный режим. Выполнены два пилота и основной прогон; в основном успешно завершены 17 из 18 попыток. Одна остановилась из-за ошибки проверки корректного отказа. На пяти успешных парах с изменившимися условиями автоматика убрала по одной ручной команде; общий вывод о преимуществе пока неубедителен. Подробности — в [отчёте о пересогласовании](documents/evaluation/reapproval.md). Реальные CRM, доставка сообщений, платежи и авторизация сотрудников не подключены.

## Запуск рабочего места

Нужны Python 3.12, uv и подготовленное окружение соседнего репозитория `tau2-bench`. Команды PowerShell из корня `ai-support-agent`:

```powershell
uv pip install --python ..\tau2-bench\.venv\Scripts\python.exe -e ".[dev]"
$env:SUPPORT_AGENT_MODE = 'demo'
..\tau2-bench\.venv\Scripts\python.exe -m streamlit run src\support_agent\ui.py --server.address 127.0.0.1 --server.headless true --browser.gatherUsageStats false
```

Открыть [рабочее место](http://127.0.0.1:8501). Сервер слушает только локальный адрес. Для остановки нажать `Ctrl+C` в терминале. Установка приложения в окружение τ-bench обязательна до первого запуска.

Учебный сценарий:

1. Выбрать клиента по имени и email, нажать «Новое обращение».
2. Ввести, например, «Обменяйте товар на любой другой доступный вариант. Email ваш@email» или «Хочу вернуть товар. Email ваш@email». Подставить email выбранного клиента и нажать «Подготовить решение».
3. Проверить историю, источники, товар, сумму, способ оплаты и точный текст. Заглушка ищет доставленный заказ среди первых шести заказов клиента, выбирает одну позицию и первый другой доступный вариант; произвольные предпочтения по цвету и другим свойствам она не разбирает.
4. Подтвердить отправку запроса условий клиенту. В блоке «Ответ клиента — тестовый канал» ввести ответ и нажать «Клиент согласен» либо «Клиент отказался».
5. При согласии клиента проверить новое предложение «Действие и ответ» и отдельно подтвердить его. При отклонении сотрудником указать причину: новый проект снова потребует согласования.

Ответ клиента здесь имитирует оператор. Кнопки фиксируют явный выбор; приложение не проверяет согласие автоматически по свободному тексту. Локальный сотрудник имеет фиксированный идентификатор `demo-employee`, реального входа и управления ролями нет.

Обмен создаёт статус `exchange requested`, возврат — `return requested`. Деньги не списываются и не возвращаются; письмо не отправляется. Тестовая доставка сохраняет утверждённый текст в SQLite. Повтор после сбоя доставки отправляет прежний текст без повторения операции.

После перезапуска выберите сохранённое обращение. Если операция уже записана, но ответ остался в очереди, нажмите «Продолжить отправку»; при ошибке доставки — «Повторить отправку». Обе команды используют прежнее согласование, текст и идентификатор сообщения. Само открытие экрана ничего не отправляет.

Если условия изменились, старое предложение блокируется, а согласие клиента отзывается. В режиме `manual` сотрудник видит причину и нажимает «Продолжить расследование». В режиме `auto` карточка показывает значения «было / стало», и приложение готовит новую версию автоматически. Для неё снова нужны подтверждение отправки условий, ответ клиента и подтверждение действия сотрудником. Повторная смена цены запускает тот же процесс; отказ клиента останавливает его, даже если цена уже изменилась.

## Данные и режим модели

| Настройка | Поведение |
|---|---|
| `SUPPORT_AGENT_MODE` | `demo` по умолчанию; `api` нужно включить явно в окружении процесса |
| `SUPPORT_AGENT_RECOVERY_MODE` | `manual` по умолчанию; `auto` включает показ разницы и автоматическую подготовку новой версии. Согласования остаются ручными |
| `SUPPORT_AGENT_DB` | Рабочая SQLite; по умолчанию `var/support.sqlite3` относительно корня приложения |
| `SUPPORT_AGENT_RETAIL_DB` | Исходный `db.json`; по умолчанию `../tau2-bench/data/tau2/domains/retail/db.json`. `policy.md` читается рядом с ним |
| `OPENAI_API_KEY`, `OPENAI_MODEL` | В режиме `api` берутся из окружения либо `.env` корня приложения; окружение имеет приоритет. Модель по умолчанию — `gpt-6-luna` |

Исходный магазин и правила копируются в рабочую SQLite только при её первой инициализации. Следующие запуски читают сохранённый снимок и историю; изменение исходного `db.json` или `policy.md` не обновляет существующую рабочую базу. Оригинальные данные τ-bench не изменяются.

Для нового учебного прогона остановить сервер и выбрать ещё несуществующий файл, сохранив прежнюю историю:

```powershell
$env:SUPPORT_AGENT_DB = 'var/support-new.sqlite3'
```

Затем повторить команду запуска Streamlit. Изменение режима, путей, ключа или модели также требует перезапуска сервера.

Для работы с моделью задать ключ в окружении либо `.env` корня приложения по [.env.example](.env.example), установить `$env:SUPPORT_AGENT_MODE = 'api'` и перезапустить сервер. Подготовка решения и его пересмотр могут обращаться к API. Создание сервиса само модель не вызывает. В режиме `demo` файл с ключами не читается. Проверки приложения выполнены без оплачиваемых вызовов модели.

Режим пересогласования задаётся независимо от модели, например `$env:SUPPORT_AGENT_RECOVERY_MODE = 'auto'` перед запуском. Переключателя внутри обращения нет. При остановке процесса во время подготовки новая версия автоматически не возобновляется: новое сообщение клиента отменяет незавершённое продолжение и начинает расследование заново.

## Проверки и отдельный пример ядра

Полный набор проверок запускается в окружении τ-bench после установки приложения командой выше:

```powershell
$env:TAU2_DATA_DIR = (Resolve-Path ..\tau2-bench\data).Path
..\tau2-bench\.venv\Scripts\python.exe -m pytest
```

Проверки используют заглушки модели, отдельные временные базы и Streamlit AppTest; реальные ключи не нужны. Они охватывают ядро, источники, согласования, исполнение, сохранение состояния и экран сотрудника.

Для независимого примера ядра без τ-bench:

```powershell
uv sync --locked --extra dev
uv run --locked python -m support_agent.demo
```

Эта установка содержит ядро и Streamlit, но не пакет `tau2`. Для рабочего места с магазином нужен описанный выше запуск из окружения τ-bench. Отдельный `support_agent.demo` использует синтетический заказ и заранее заданные ответы; показывает предложение отмены, ничего не отменяя и не отправляя.

## Общее ядро и τ-bench

`AgentCore(model=..., policy=..., tools=..., language="ru")` получает адаптер с методом `generate(messages, tools)`. `step(incoming, state)` возвращает `Generation` и новое `AgentState`, не меняя переданное состояние. Ядро проверяет имя инструмента и JSON Schema аргументов; запись и отправку выполняет вызывающая сторона после своих проверок.

В приложении `propose_exchange` и `propose_return` готовят предложения. В штатном испытании `HalfDuplexAgent` возвращает исходные инструменты среде τ-bench; дополнительного согласования сотрудником там нет. Скрытые инструкции клиента и `evaluation_criteria` ядру не передаются.

Используется [τ-bench](https://github.com/sierra-research/tau2-bench), commit `da0835f6c67baef58bdda18f2a3b037dfb3a1754`. Задания, правила и инструменты исходной оценки сохраняются. Сухая проверка контрольной задачи 75 сверяет настройки, commit и хеши, не читает `.env` и не вызывает API:

```powershell
..\tau2-bench\.venv\Scripts\python.exe evals\core-integration\run_control.py --repo ..\tau2-bench --dry-run
```

Оплачиваемый прогон требует явного `--run`, нового каталога и ключа в `../tau2-bench/.env` либо окружении процесса. Это отдельные настройки испытаний; рабочее место читает `.env` самого приложения.

```powershell
..\tau2-bench\.venv\Scripts\python.exe evals\core-integration\run_control.py --repo ..\tau2-bench --run --run-dir evals\core-integration\new-attempt
```

Скрипт фиксирует `openai/responses/gpt-6-luna`, параметры исходной оценки, одну попытку и `workers=0`. В Windows он временно добавляет доверенные системные сертификаты к certifi, сохраняя проверку TLS. Секреты удаляются из сохраняемых текстовых материалов. Повтор успешного прогона нужен после значимого изменения, а не правок пояснений.

## Сравнение пересогласования

Испытания в `evals/reapproval` используют синтетический магазин и фиксированные действия клиента и сотрудника. Это отдельное сравнение двух режимов приложения; исходные задания τ-bench не меняются. Удобство работы реального сотрудника здесь не измеряется.

Проверка процесса без API в новом каталоге:

```powershell
..\tau2-bench\.venv\Scripts\python.exe evals\reapproval\run_reapproval.py --offline --run-dir evals\reapproval\runs\offline-check
```

Она выполняет шесть проходов с заглушкой. Это не оплачиваемый пилот и не оценка качества языковой модели. Результат сохраняется в `offline/manifest.json`.

Для оплачиваемой серии предусмотрены команды:

```powershell
..\tau2-bench\.venv\Scripts\python.exe evals\reapproval\run_reapproval.py --run --phase pilot --repo ..\tau2-bench --budget-usd 5 --run-dir evals\reapproval\runs\series-1
# Основной прогон — после разбора технически готового пилота, если продолжение обосновано.
..\tau2-bench\.venv\Scripts\python.exe evals\reapproval\run_reapproval.py --run --phase main --repo ..\tau2-bench --budget-usd 5 --run-dir evals\reapproval\runs\series-1
```

Пилот содержит 6 попыток, основной прогон — 18; пилот в итоговое сравнение не входит. Для обоих этапов нужен один каталог серии: `budget.json` учитывает подготовку и все запросы в пределах согласованных **5 USD**. Основной прогон требует завершённого технически готового оплачиваемого пилота и совпадения хешей кода, данных и настроек. Ключ читается из окружения либо `.env` соседнего τ-bench только при `--run`.

В сравнении закреплены `openai/responses/gpt-6-luna`, `reasoning_effort=low`, `max_tokens=8192`, тайм-аут запроса до 90 секунд, ноль повторов API и попытки. На всю попытку с пересогласованиями допускаются 60 шагов и 600 секунд; шагом считается вызов модели, её инструмент или действие имитируемого сотрудника. Эти ограничения относятся к скрипту сравнения: в режиме API рабочего места сохранён один технический повтор запроса.

Каждая пара начинается с копий одной SQLite после согласия клиента, перед окончательным подтверждением сотрудника. Отчёт сохраняет состояния, вызовы, расходы и дополнительные вмешательства (`manual_resume` и `rejected`); обязательные подтверждения учитываются отдельно. Исходный пилот сохранён в `evals/reapproval/2026-10-31`, согласованный повтор и основной прогон — в `evals/reapproval/2026-10-31-revised`. Всего выполнены разрешённые 30 попыток; общий учтённый расход с подготовкой — **0,0133641 USD**. Журнал новой серии уже включает первый пилот: складывать оба журнала нельзя. Код между повторным пилотом и основным прогоном не менялся. Результаты и ограничения — в [отчёте](documents/evaluation/reapproval.md), протокол — в [описании испытания](evals/reapproval/README.md).
