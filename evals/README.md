# Оценка агента

`evals/` содержит скрипты запуска и сохранённые результаты испытаний. Здесь нет исходного датасета τ-bench и кода рабочего приложения. Выводы по результатам хранятся в [documents/evaluation](../documents/evaluation/retail-baseline.md).

## Что запустить

Команды выполняются из корня проекта в PowerShell, после [установки рабочего места](../README.md#запуск-рабочего-места) с дополнениями `retail` и `dev`.

| Задача | Инструкция |
|---|---|
| Проверить приложение без ключей | [pytest, Ruff и пример ядра](#проверки-без-api) |
| Проверить общее ядро на задаче 75 τ-bench | [Подготовка данных и контрольный запуск](#подключение-общего-ядра) |
| Сравнить ручное и автоматическое пересогласование | [README стенда](reapproval/README.md) |
| Проверить расследование на известных или новых обращениях | [README стенда](investigation/README.md) |
| Пройти три сценария на экране | [Инструкция приёмки](../documents/evaluation/acceptance.md) |

## Проверки без API

```powershell
.\var\runtime\Scripts\python.exe -m pytest
.\var\runtime\Scripts\python.exe -m ruff check .
```

Проверки используют подставную модель, временные базы и Streamlit AppTest. Они охватывают ядро, источники, согласования, исполнение, сохранение состояния и экран; реальные ключи не нужны.

[GitHub Actions](../.github/workflows/checks.yml) запускает pytest и Ruff при `push` и `pull_request`: Windows, Python 3.12.12, uv 0.10.4, зависимости из `uv.lock` с дополнениями `retail` и `dev`. Ключи модели и Zammad не подключаются. Ошибка любой проверки делает запуск неуспешным; Ruff выполняется и после ошибки pytest. В таком запуске **Artifacts → pytest-report** содержит отчёт JUnit XML.

Отдельный пример ядра:

```powershell
.\var\runtime\Scripts\python.exe -m support_agent.demo
```

Он использует синтетический заказ и заранее заданные ответы модели: показывает предложение отмены, ничего не отменяя и не отправляя. Это пример вызова ядра, не полное рабочее место или штатная оценка τ-bench.

## Файлы отдельного запуска

Внутри каталогов запусков и диагностики:

- **`run_manifest.json`** — модели и настройки, ограничения, время запуска, краткие статусы задач, SHA256 исходных файлов до и после. `input_files_unchanged` показывает, изменились ли проверяемые исходные файлы.
- **`results.json`** — штатный результат τ-bench: `info` описывает конфигурацию и среду, `tasks` содержит задания и критерии, `simulations` — диалоги, инструменты, причины завершения и оценки. Наличие критериев в сохранённом файле не означает их передачу агенту поддержки.
- **`artifacts/task_<ID>/sim_<UUID>/task.log`** — подробный журнал выполнения.
- **`artifacts/.../llm_debug/*.json`** — отдельные запросы и ответы моделей с токенами и временем генерации, включая текстового оценщика.

Абсолютные пути временных каталогов в манифестах — пути на момент запуска. Материалы затем перенесены в проект; их нынешнее расположение указано выше. Исторические настройки не переписывались.

## Как читать статусы

`run_manifest.status = "finished"` означает завершение запуска, **а не успешное решение задачи**. Такое значение есть и у `diag/tls/run_manifest.json`.

Проверять нужно соответствующую запись в `results.json` → `simulations`:

| Значение | Смысл |
|---|---|
| `termination_reason = "infrastructure_error"`, `reward_info = null` | Технический сбой; оценки качества нет |
| `reward_info.reward = 0` | Завершённый диалог не выполнил штатные критерии |
| `reward_info.reward = 1` | Штатные критерии выполнены, но они не покрывают все правила обслуживания |

Итог серии — 4 из 5. У задачи 95 ручной разбор обнаружил несогласованный способ оплаты при балле 1. У 105 балл 0 связан с невозможным эталонным обменом при исходном балансе карты. Подробности приведены в [отчёте](../documents/evaluation/retail-baseline.md); сами оценки не исправлялись.

## Хранение и повторный запуск

В Git остаются README, [run_baseline.py](retail-baseline/run_baseline.py), манифесты, исходные `results.json`, читаемые диалоги, предварительная проверка и итоговая сводка. Согласно `.gitignore`, подробные журналы в `artifacts/` остаются локально и могут отсутствовать после клонирования.

`summary.json` и `dialogues/` производны от исходных результатов. Для проверки спорной оценки следует открыть соответствующий `results.json` и разбор в отчёте. Новые эксперименты сохраняются отдельно, без перезаписи этой серии.

Команды просмотра и повторного запуска находятся в [отчёте](../documents/evaluation/retail-baseline.md#просмотр-и-повторный-запуск). Просмотр сохранённых результатов и `--dry-run` не вызывают модель; обычный запуск обращается к API.

## Подключение общего ядра

`core-integration/run_control.py` проверяет общее ядро на одной задаче 75 с настройками исходной оценки. Это отдельная серия; она не заменяет `retail-baseline` и не доказывает улучшение качества.

В приложении `propose_exchange` и `propose_return` готовят предложения. В штатном испытании `HalfDuplexAgent` возвращает исходные инструменты среде τ-bench; дополнительного согласования сотрудником там нет. Скрытые инструкции клиента и `evaluation_criteria` ядру не передаются.

Пакет [τ-bench](https://github.com/sierra-research/tau2-bench) закреплён на commit `da0835f6c67baef58bdda18f2a3b037dfb3a1754` в `pyproject.toml` и `uv.lock`. Для исходных задач и проверки манифестов нужен отдельный checkout этой версии с полными данными. `evals/reapproval/base_shop.json` его не заменяет.

Следующие команды нужны для испытаний, не для запуска учебного рабочего места. Используйте новый каталог `var/tau2-source`; существующий соседний репозиторий не меняйте:

```powershell
git clone --filter=blob:none --no-checkout https://github.com/sierra-research/tau2-bench.git var/tau2-source
git -C var/tau2-source checkout --detach da0835f6c67baef58bdda18f2a3b037dfb3a1754
$env:TAU2_DATA_DIR = (Resolve-Path var/tau2-source/data).Path
```

Задания, правила и инструменты исходной оценки сохраняются. Сухая проверка задачи 75 сверяет настройки, commit и хеши, не читает `.env` и не вызывает API:

```powershell
.\var\runtime\Scripts\python.exe evals\core-integration\run_control.py --repo var/tau2-source --dry-run
```

Оплачиваемый прогон требует отдельного решения о запуске, явного `--run`, нового каталога и ключа в окружении процесса либо `.env` выбранного checkout (`var/tau2-source/.env` для команды ниже). Это отдельные настройки испытаний; рабочее место читает `.env` самого приложения.

```powershell
.\var\runtime\Scripts\python.exe evals\core-integration\run_control.py --repo var/tau2-source --run --run-dir evals\core-integration\new-attempt
```

Скрипт фиксирует `openai/responses/gpt-6-luna`, параметры исходной оценки, одну попытку и `workers=0`. В Windows он временно добавляет доверенные системные сертификаты к certifi, сохраняя проверку TLS. Секреты удаляются из сохраняемых текстовых материалов. Повтор успешного прогона нужен после значимого изменения, а не правок пояснений.

Скрипт сохраняет `run_manifest.json` и штатный `results.json`. Для [попытки 2026-10-30](core-integration/2026-10-30/) при разборе дополнительно подготовлены производная `summary.json` и читаемый `dialogue.md`; скрипт не создаёт их автоматически. В локальном `artifacts/agent_calls/` находятся запросы и ответы нашего ядра; журналы имитатора остаются в штатных `artifacts/.../llm_debug/`. Весь `artifacts/` исключён из Git.

Результаты и ограничения — в [отчёте о подключении](../documents/evaluation/core-integration.md).

## Пересогласование после изменения условий

`reapproval/` содержит собственные синтетические случаи и стенд сравнения ручной и автоматической повторной подготовки. Оба режима начинают с одной копии SQLite после согласия клиента, перед окончательным подтверждением сотрудника. Проверяются неизменные условия, новая цена и отменённый заказ. Клиент и сотрудник имитируются по заданным правилам; время реального человека не измеряется.

Первый оплачиваемый пилот от 31 октября 2026 года получил **5/6** по первоначальной автоматической проверке. В шестой попытке агент подготовил корректный отказ, но текстовая эвристика его не распознала и остановила процесс до доставки. Исходные оценки сохранены. Исправление выполнено без API: прошли 24 теста стенда и 206 тестов полного набора. Учтённый расход с подготовкой — **$0.003512**.

Выполнены все **30 разрешённых попыток** при общем лимите **$5**. [Повторный пилот](reapproval/2026-10-31-revised/pilot/manifest.json) получил **6/6**, [основной прогон](reapproval/2026-10-31-revised/main/manifest.json) — **17/18**: ручной режим 8/9, автоматический 9/9. Во втором случае ошибочной оценки эвристика приняла отрицание «подтвердить его не получится» за запрос согласия и остановила корректный отказ до доставки. Оценщик и исходный результат не исправлялись, попытка не повторялась.

На пяти успешных парах с изменением условий автоматический режим устранил одну команду повторной подготовки; на трёх неизменных парах разницы нет. Одна неполная пара исключена из расчёта и сохранена отдельно. **Общее преимущество не доказано; ручной режим остаётся основным, автоматический — экспериментальным.** Разницу 8/9 против 9/9 нельзя трактовать как преимущество качества.

## Чистая установка и восстановление — 31 октября 2026 года

`startup/` содержит скрипты `check_ui.py`, `check_lifecycle.py` и `check_server.py`. Они проверяют настоящий экран через Streamlit AppTest, восстановление в отдельных процессах и запуск HTTP-сервера; API не используют. Все сценарии работают на отдельном синтетическом снимке, рабочие SQLite исключены из Git.

В `startup/2026-10-31/` сохранены `validation.json` с версиями, хешами и аудитом материалов, `pytest.xml` с 206 успешными проверками, а также результаты и журналы в `ui-check/`, `lifecycle/` и `server/`.
